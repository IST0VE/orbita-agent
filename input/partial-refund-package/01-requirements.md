# 01. Системные требования: частичный возврат заказа

**Задача:** дать оператору вернуть деньги за отдельные позиции заказа, не
отменяя заказ целиком.

## Цель системы

Оператор клиентского сервиса возвращает клиенту деньги за выбранные позиции
заказа. Заказ при этом остаётся в системе, остальные позиции клиента не
затрагиваются. Возврат доходит до эквайера один раз, в правильной сумме,
с учётом скидки на заказ.

## Actors

- **Оператор клиентского сервиса** — инициирует возврат в админке;
- **Клиент** — получает деньги и уведомление; в первой версии сам возврат
  не оформляет;
- **Бухгалтерия** — получает проводки через существующую интеграцию с 1С;
- **Эквайер** — внешняя система, исполняет возврат по платежу.

## Основные use cases

1. Оператор возвращает одну позицию из заказа.
2. Оператор возвращает несколько позиций одной операцией.
3. Оператор возвращает последние оставшиеся позиции — заказ закрывается
   полностью возвращённым.
4. Возврат не проходит на стороне эквайера, оператор видит причину.

## Функциональные требования

- ФТ-1. Оператор выбирает одну или несколько позиций заказа и инициирует
  возврат одной операцией. Позиция выбирается целиком; частичный возврат
  количества внутри позиции в первой версии не поддерживается.
- ФТ-2. Возврат допускается для заказов в статусах `paid`, `shipped` и
  `delivered`. Для `created` возврат невозможен: денег ещё нет. Для
  `cancelled` невозможен: деньги уже возвращены отменой.
- ФТ-3. Сумма возврата за позицию считается пропорционально скидке на заказ:
  `цена позиции × (1 − скидка / сумма до скидки)`. Округление до копейки
  в пользу клиента.
- ФТ-4. При возврате последней невозвращённой позиции остаток от округления
  добавляется к сумме операции так, чтобы сумма всех возвратов по заказу
  совпала с оплаченной суммой.
- ФТ-5. Повторный возврат одной и той же позиции невозможен. Попытка
  отклоняется с указанием, какие именно позиции уже возвращены.
- ФТ-6. Каждая операция возврата идемпотентна по ключу, который формирует
  вызывающая сторона. Повтор с тем же ключом возвращает результат первой
  операции и не создаёт вторую.
- ФТ-7. Оператор может отменить возврат, находящийся в статусе `pending`,
  если эквайер ещё не подтвердил операцию.
- ФТ-8. Стоимость доставки не возвращается ни при каком составе возврата.
  Решение зафиксировано финансами 26 августа.
- ФТ-9. При возврате позиции заказа в статусе `shipped` позиция снимается
  с доставки. Если снять её невозможно, возврат не выполняется, и оператор
  получает причину.

## Нефункциональные требования

- НФТ-1. Эквайер принимает не более 20 операций возврата по одному платежу.
  Система обязана укладываться в этот лимит при любом составе возвратов.
- НФТ-2. Ответ на запрос возврата — не дольше 3 секунд при доступном
  эквайере. Подтверждение эквайера асинхронное и в это время не входит.
- НФТ-3. Все операции возврата хранятся не менее 5 лет: срок исковой
  давности.
- НФТ-4. Двойной возврат по одному платежу недопустим ни при каких сетевых
  отказах. Это требование сильнее доступности: при сомнении система обязана
  отказать, а не повторить.

## Жизненный цикл заказа

Статусы: `created`, `paid`, `shipped`, `delivered`, `cancelled`,
`partially_refunded`, `refunded`.

Переходы:

- `created → paid → shipped → delivered`;
- `created → cancelled`, `paid → cancelled`;
- `paid → partially_refunded`, `shipped → partially_refunded`,
  `delivered → partially_refunded` — после первого частичного возврата;
- `partially_refunded → partially_refunded` — каждый следующий частичный;
- `partially_refunded → refunded` — когда возвращены все позиции;
- `delivered → refunded` — возврат всего заказа одной операцией.

Переходы, которых быть не должно: любой переход из `refunded` и
`cancelled`; переход `partially_refunded → delivered`.

## Жизненный цикл возврата

`pending → settled` или `pending → rejected`. Из `pending` возможна отмена
оператором: `pending → cancelled`. Терминальные: `settled`, `rejected`,
`cancelled`.

## Идемпотентность

Ключ формирует админка: `order_id` + отсортированный список `item_id` +
идентификатор попытки оператора. Ключ живёт TBD и хранится вместе с
результатом первой операции.

## Поведение при отказах

| Сценарий | Что видит оператор | Состояние системы |
|---|---|---|
| эквайер не ответил за таймаут | «возврат отправлен, статус уточняется» | возврат в `pending`, повтор запрещён |
| эквайер отказал | причина отказа от эквайера | возврат в `rejected`, позиции не помечены возвращёнными |
| позицию не удалось снять с доставки | «возврат не выполнен: позиция уже передана курьеру» | изменений нет |
| исчерпан лимит 20 операций | «по этому заказу больше нельзя вернуть частями» | изменений нет |

## Edge cases

1. Сумма возвратов сравнялась с суммой заказа — заказ переходит в `refunded`.
2. Заказ оплачен двумя платежами — в первой версии не поддерживается, возврат
   отклоняется.
3. Валюта возврата отличается от валюты платежа — невозможно, возврат всегда
   в валюте платежа.
4. Нулевая сумма возврата после применения скидки — операция не создаётся.

## Явные допущения

1. Интеграция с 1С не дорабатывается: она читает события заказа и новых
   полей не требует.
2. Личный кабинет клиента возвратов не оформляет — только оператор.
3. Один заказ — один платёж.

## Вопросы к заказчику

1. Что показывать клиенту, пока эквайер не подтвердил возврат: списание уже
   произошло на нашей стороне, но денег на карте ещё нет.
2. Срок «возврат за 3 дня» из исходной задачи относится к решению оператора
   или к деньгам на карте клиента? Второе от нас не зависит.
3. Нужно ли уведомлять клиента о каждом частичном возврате отдельно или одним
   письмом по завершении.
