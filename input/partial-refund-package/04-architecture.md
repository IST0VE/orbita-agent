# 04. Архитектура решения: частичный возврат

## Компоненты

| Сервис | Компонент | Что делает | Слой |
|---|---|---|---|
| `admin-ui` | экран заказа | выбор позиций, кнопка возврата, статус операции | frontend |
| `orders-api` | `RefundController` | REST из документа 02, валидация входа | backend |
| `orders-api` | `RefundService` | расчёт суммы, проверка ФТ-5, оркестрация | backend |
| `orders-api` | `IdempotencyStore` | ключи и сохранённые ответы по ФТ-6 | backend |
| `orders-api` | `RefundRepository` | таблицы `refunds` и `refund_items` | data |
| `billing` | `AcquirerGateway` | обращение к эквайеру, обработка отказов | integration |
| `delivery` | `RecallApi` | снятие позиции с доставки для ФТ-9 | integration |
| `notifications` | подписчик `orders.events` | письмо клиенту | backend |
| `1c-integration` | подписчик `orders.events` | проводки | integration |

## Поток создания возврата

1. Оператор выбирает позиции в `admin-ui`, интерфейс формирует ключ
   идемпотентности и вызывает `POST /orders/{order_id}/refunds`.
2. `RefundController` проверяет статус заказа и состав позиций.
3. `IdempotencyStore` смотрит ключ. Найден — отдаётся сохранённый ответ, дальше
   ничего не происходит.
4. `RefundService` считает сумму пропорционально скидке; при возврате
   последних позиций добавляет остаток округления.
5. Для заказа в `shipped` вызывается `delivery.RecallApi`. Отказ — возврат
   не создаётся.
6. Запись `refunds` в статусе `pending` и записи `refund_items` создаются
   одной транзакцией с резервированием позиций.
7. `billing.AcquirerGateway` отправляет возврат эквайеру.
8. Подтверждение эквайера приходит вебхуком, `RefundService` переводит возврат
   в `settled` и публикует `refund.settled`.
9. Если возвращены все позиции заказа, заказ переходит в `refunded`, иначе —
   в `partially_refunded`.

## Идемпотентность

Ключ хранится в `IdempotencyStore` вместе с телом ответа. Срок жизни ключа —
**7 дней**: короче эквайерского окна разбора спорных операций.

Запись ключа и создание возврата идут в одной транзакции. Это и есть механизм
НФТ-4: двойного возврата не может быть даже при повторе после таймаута, потому
что второй запрос увидит ключ до обращения к эквайеру.

## Ограничение эквайера

`AcquirerGateway` считает число операций возврата по `payment_id` и отклоняет
двадцать первую. Счётчик берётся из таблицы `refunds`, отдельного хранилища
не нужно.

## Отказоустойчивость

- таймаут к эквайеру — 5 секунд, ретраев на запись нет: повтор делает оператор
  тем же ключом;
- вебхук эквайера идемпотентен по `acquirer_ref`;
- зависший `pending` дольше 24 часов попадает в отчёт для ручного разбора;
- недоступность `delivery` для заказа в `shipped` означает отказ в возврате,
  а не возврат без снятия с доставки.

## Наблюдаемость

Метрики: число возвратов по статусам, время до `settled`, доля `rejected`,
число конфликтов идемпотентности. Алерт на рост `pending` — по НФТ-2 и
NFR-9.

Логи: `refund_id`, `order_id`, `payment_id`, ключ идемпотентности в каждой
записи. Сумма и позиции не логируются в открытом виде.

## Совместимость

`GET /orders/{order_id}/refunds` для списка возвратов по заказу добавляется
позже, вместе с личным кабинетом. Существующий `POST /orders/{order_id}/refund`
(без `s`, возврат целиком) остаётся и переводится на тот же `RefundService`
внутри — снаружи контракт не меняется.

## Что не решено

- архивация возвратов старше 5 лет;
- поведение при заказе, оплаченном двумя платежами: сейчас отклоняется, но
  такие заказы появятся вместе с оплатой частями.
