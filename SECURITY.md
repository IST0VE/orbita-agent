# Безопасная эксплуатация

[Обзор проекта](README.md) · [Развёртывание](docs/DEPLOYMENT.md) · [Конфигурация](docs/CONFIGURATION.md)

Orbita читает материалы задач, вызывает платную модель и может записывать страницы Confluence и задачи Jira. Текущая конфигурация предназначена для локального оператора.

## Доступ к серверу

Штатный Compose публикует backend только на `127.0.0.1:2024`. Команды локального запуска также ограничивают backend и Vite loopback-адресом.

`API_ADMIN_TOKEN` обязателен для всего API: `/api/*`, `/assistants`, `/threads`, `/runs`, `/store`, метаданных и других маршрутов. Пустое значение или токен вне диапазона 32–256 ASCII-символов закрывает доступ с HTTP 503; неверный или отсутствующий Bearer возвращает 401. Исключений для localhost, proxy-заголовков и OPTIONS нет. WebSocket закрыт; frontend использует SSE. Токен хранится в `sessionStorage` текущей вкладки и передаётся также при запуске графов.

Сгенерируйте токен командой `python -c "import secrets; print(secrets.token_urlsafe(32))"`, запишите в `.env` или окружение сервера и перезапустите сервер. Токен нельзя изменить через HTTP API. Middleware подключается глобально через `http.app` и `middleware_order: middleware_first`; смена порядка требует повторной проверки защиты всех маршрутов. Ответы API запрещают кеширование, тело каждого запроса ограничено `API_MAX_REQUEST_BYTES`, чтение тела — 30 секундами.

Для Docker Compose нужен и отдельный случайный `NT_RUNNER_TOKEN` не короче 16 символов: им агент авторизуется у runner нагрузочного тестирования. `up.cmd` / `up.sh` генерируют оба токена, если строки пусты. Runner в Compose слушает только сеть Compose: порт на хост не опубликован, а управляющий API без токена отвечает 401. Цели нагрузки по-прежнему ограничены списком `config/nt-runner.json`, подключённым к контейнеру только на чтение.

`/metrics` закрыт тем же входом, что и весь API. Prometheus из профиля `monitoring` приходит с отдельным `METRICS_TOKEN`: он открывает только `GET /metrics`, а на `/api/*`, тредах и прогонах получает 401. В метриках нет текста задач, идентификаторов тредов и пользователей — только счётчики по графам, узлам, моделям и кодам ответа. Prometheus и Grafana слушают только петлю; доску Grafana можно смотреть без входа, поэтому наружу её открывают, как и интерфейс, только через reverse proxy с аутентификацией.

PostgreSQL в Compose поднимается всегда: в нём личные подключения пользователей, а в серверном режиме — и база Keycloak. Для него нужен отдельный случайный URL-safe `POSTGRES_PASSWORD`, `up.cmd` / `up.sh` создают его сами; пароля по умолчанию нет. Порт базы открыт только на петлю. У существующего тома PostgreSQL изменение переменной не меняет пароль роли в базе: согласуйте смену пароля до перезапуска, не удаляя том с данными.

Общий административный токен не разделяет пользователей и их данные. Для команды разворачивается [сервер с доменом](docs/DEPLOYMENT.md#сервер-с-доменом): HTTPS на корпоративном прокси, вход через Keycloak, у каждого свои треды, файлы, документы и токены Jira. Что при этом остаётся на администраторе сервера — [ниже](#перед-тем-как-пустить-на-сервер-команду). Штатный frontend работает через один origin (Vite proxy); прямой cross-origin доступ и его CORS-политика требуют отдельной настройки.

## Ключи и материалы

- Храните ключи в корневом `.env` или окружении процесса. `.env` исключён из Git; `.env.example` должен содержать только шаблонные значения.
- Не помещайте ключи в `VITE_*`: значения сборки frontend доступны браузеру.
- Файлы, загруженные в чат, видит только владелец чата: папка лежит под тредом, и граф получает её по треду прогона, а не по имени из запроса. Текст файлов чата передаётся модели.
- `AGENT_INPUT_DIR` — общая библиотека примеров, её видит каждый вошедший. Кладите туда только то, что можно показывать всем.
- Для аналитики и подготовки задачи инструменты могут читать соседние файлы того же чата. Разделяйте независимые материалы по разным чатам.
- Маскирование при публикации не означает маскирования до отправки модели. Подготовьте допустимый к обработке вход заранее.

Настройки UI возвращают секреты маской и не раскрывают их значение. Это не делает весь сервер безопасным для анонимного доступа: он также читает документы и запускает обработку.

Через настройки можно сохранять только документированные переменные приложения; произвольные имена и управление токеном запрещены. Адреса Jira и Confluence, их `*_ALLOW_INSECURE_HTTP` и адрес runner правятся только в `.env` на сервере: туда уходят личные токены всех пользователей, и смена адреса из интерфейса собрала бы их на чужом сервере. Адрес модели и адреса источников НТ из интерфейса сменить можно, но только вместе с токеном, который на них уйдёт: иначе сохранение откажет. Неизвестные переменные при чтении маскируются. Подстановка `${...}` в сохраняемых значениях запрещена. На POSIX новый `.env` создаётся с правами `0600`; Windows требует корректных ACL каталога. Файлы `.env*`, `*.env`, `*.pem` и `*.key` не читаются через инструменты материалов. Остальные входные документы всё равно должны быть заранее проверены на секреты.

## Внешние действия

Оставляйте `PUBLISH_REQUIRE_APPROVAL=1` и `JIRA_CREATE_REQUIRE_APPROVAL=1` для интерактивной работы. Перед согласием проверяйте назначение, заголовки, содержимое и действие создания/обновления.

Создание черновика Confluence тоже записывает объект во внешнюю систему. Подготовка ручной формы Jira сама не доказывает создание задачи. При частичной ошибке уже выполненные действия не откатываются автоматически.

HTTP для удалённых Jira/Confluence по умолчанию запрещён; локальные адреса имеют отдельное исключение. Параметры `*_ALLOW_INSECURE_HTTP` предназначены для явно настроенного исключения.

Jira/Confluence не следуют HTTP-перенаправлениям, включая 307/308 с телом документа: настройте конечный адрес API. Переопределения адреса LLM требуют HTTPS (HTTP разрешён только для loopback), без credentials, query и fragment.

## Маскирование и бюджет

Публикуемый текст проходит встроенное маскирование распространённых секретов. Дополнительные шаблоны задаются через `CONFLUENCE_MASK_PATTERNS`, разделённые `||`; строка замены — `CONFLUENCE_MASK_REPLACEMENT`. Автоматическое распознавание не гарантирует удаления всех чувствительных данных.

`BUDGET_USD_PER_THREAD` проверяет накопленную расчётную стоимость до следующего вызова. Он требует корректного тарифа и не гарантирует точного потолка итогового списания. Ограничения учётной записи провайдера задаются вне Orbita.

## Движение рабочих данных

Два разных механизма легко перепутать, а последствия у них противоположные.

| | Подготовка перед передачей модели | Маскирование при публикации |
| :--- | :--- | :--- |
| Кто отвечает | Оператор: что загрузил в чат, то и уедет | Код: `agent/outgoing.py` |
| Когда срабатывает | Никогда автоматически | Перед записью в файл, Confluence и Jira |
| Что закрывает | Ничего: текст файлов, история треда и ответы инструментов уходят провайдеру как есть | Известные секреты в исходящем тексте, плюс `CONFLUENCE_MASK_PATTERNS` |

Маскирование публикации не защищает передачу модели. Материал, который нельзя отправлять провайдеру, не должен попадать в чат.

### Где оседают материалы

| Хранилище | Что в нём | Настройка | Как удалить |
| :--- | :--- | :--- | :--- |
| Чекпоинты треда | Полная история: вопросы, документы этапов, ответы инструментов, план публикации | `CHECKPOINT_BACKEND=memory` (по умолчанию, живёт до перезапуска процесса) или `postgres` с `POSTGRES_URI` | `memory` — перезапуск процесса; `postgres` — удаление треда или базы средствами СУБД |
| Хранилище `langgraph dev` | То же для тредов dev-сервера | Управляется самим сервером, каталог `.langgraph_api/` | Удаление каталога; в контейнере — пересоздание контейнера |
| Файлы чатов | Загруженные в чат файлы и копии из библиотеки | `CHAT_FILES_DIR`, по папке на тред; в Docker — `/data/chats` | Удаление чата в интерфейсе; папки тредов, удалённых мимо интерфейса, убирает фоновая уборка |
| Долгая память | Короткие резюме по аккаунтам между тредами, своё пространство у каждого пользователя | `MEMORY_ENABLED`; хранилище — то же, что у чекпоинтов | `MEMORY_ENABLED=0` и очистка хранилища |
| Опубликованные документы | Готовые страницы в Markdown; у пользователя своя папка `users/<sub>/` | `PUBLISH_DIR` | Удаление файлов |
| Журнал операций Jira | Ключи прогонов, локальные ключи карточек, ключи заведённых задач и метки операций. Текста карточек в нём нет | `JIRA_JOURNAL_PATH` | Удаление файла; повтор после этого не узнает прошлые отправки |
| Каталог runner НТ | Сценарий k6, датасет, сводки прогонов, SQLite | `--root` у `serve_nt_runner.py`, по умолчанию `.nt-runs/`; в Docker Compose — том `nt-runs` | Удаление каталога; в Docker — `docker volume rm` тома после остановки runner |
| Трассировка LangSmith | Промпты и ответы целиком, на стороне LangSmith | `LANGSMITH_TRACING`; по умолчанию выключена и отключена в тестах принудительно | Средствами LangSmith; включать только для материалов, которые разрешено туда передавать |
| Резервные копии | Всё перечисленное выше, если попало в копию | Вне Orbita | Вне Orbita |

Поддерживаемая конфигурация без внешнего хранения: `CHECKPOINT_BACKEND=memory`, `MEMORY_ENABLED=0`, `LANGSMITH_TRACING` не задана, публикация в `PUBLISH_DIR` на локальном диске. В ней материалы живут в процессе и в файлах, которые видно и можно удалить.

Проверка секретов в репозитории — `python scripts/scan_secrets.py --mode tree`. Те же правила распознавания применяются к исходящим документам; в CI работы `secret scan` проверяют изменения, а по расписанию — историю. Значения находок не выводятся.

Полная проверка истории — `python scripts/scan_secrets.py --mode history` после установки зависимостей из `requirements.txt`; нужен клон со всей историей (`fetch-depth: 0` в CI). Исключения синтетических Bearer-токенов перечислены в `BEARER_FIXTURES` по точному пути и значению, включая прежние имена фикстур из истории. Суффикс `@object_id` в сообщении указывает Git-объект и не участвует в поиске исключения. Другой токен в том же файле или та же фикстура в другом файле остаются находкой; добавлять весь файл в `ALLOWED` для такого исключения не нужно.

## Шифрование

| Что | Зашифровано | Как |
| :--- | :--- | :--- |
| Личные токены Jira и Confluence | Да | AES-256-GCM ключом `USER_SECRETS_KEY`, привязка к пользователю и полю (`agent/credentials.py`) |
| Браузер ↔ корпоративный прокси | Да | HTTPS на прокси, HSTS отдаёт nginx в серверном режиме |
| Прокси → сервер, сервисы внутри Docker, агент → PostgreSQL | Нет | HTTP и TCP без TLS: сеть Compose и путь от прокси считаются доверенными |
| Треды, файлы чатов, документы, журнал Jira, файлы runner | Нет | Тома `threads`, `data`, `nt-runs` открытым текстом |
| PostgreSQL, база Keycloak | Нет | Том `pgdata`; пароли AD в Keycloak не хранятся, локальные — хешами Keycloak |
| `.env` со всеми общими секретами | Нет | Файл на хосте, права 600 ставит `up.sh` |

Шифровать тома по отдельности внутри приложения бессмысленно: ключ лежал бы на той же машине. Данные на диске закрывает шифрование диска хоста, и это обязательная часть установки на сервер.

### Перед тем как пустить на сервер команду

1. **Шифрование диска.** LUKS или BitLocker на разделе с `/var/lib/docker` (тома) и с каталогом проекта (`.env`). Без него копия диска или снимок ВМ отдают переписку, документы и все общие ключи.
2. **Резервные копии** шифруются и хранятся отдельно от `.env`: в копии тома `pgdata` личные токены защищает только `USER_SECRETS_KEY`.
3. **Порт `web` открыт только прокси.** Файрвол на сервере пускает к `ORBITA_WEB_PORT` лишь адрес прокси; прокси на этой же машине — `ORBITA_WEB_BIND=127.0.0.1`. Между прокси и сервером идут токены входа и `API_ADMIN_TOKEN`: если этот участок проходит через сеть, которой нет доверия, попросите у администраторов прокси TLS до сервера.
4. **Консоль Keycloak.** Временного `admin` замените постоянным администратором ([DEPLOYMENT.md](docs/DEPLOYMENT.md#первая-настройка-keycloak)). Путь `/auth/admin/` на корпоративном прокси откройте только сетям администраторов: пользователям нужен лишь вход, `/auth/realms/orbita/`.
5. **Журнал входов.** Новый realm заводится с журналом входов и действий администратора (90 дней) и блокировкой после 10 неверных паролей. Realm, созданный раньше, файл не обновит: включите в консоли Realm settings → Events (User events и Admin events, без Include representation), а в Security defenses → Brute force detection задайте Max login failures = 10.
6. **Grafana.** Том `grafana`, заведённый до случайного `GRAFANA_ADMIN_PASSWORD`, живёт с паролем `admin`: смените его ([MONITORING.md](docs/MONITORING.md)).
7. **Ничего не уходит наружу.** Трассировку LangSmith (`LANGSMITH_TRACING`) не включайте. Аналитика запуска `langgraph dev` в образе выключена (`LANGGRAPH_CLI_NO_ANALYTICS=1`). Наружу сервер ходит только к модели, Jira, Confluence и источникам НТ из `.env`.
8. **Хранение.** Треды и файлы чатов живут, пока их не удалят. Если политика компании требует срока хранения, удаляйте чаты по нему; фоновая уборка убирает только файлы уже удалённых тредов.

## Эксплуатационные проверки

Тесты блокируют реальные подключения и DNS-запросы; на Windows допускается только внутренняя socketpair для asyncio. Личные `.env` и трассировка отключены в тестах. Ruff проверяет опасное исполнение кода, десериализацию, shell и отключение TLS. CI также проверяет зависимости через pip-audit и npm audit. Эти проверки не доказывают отсутствие всех уязвимостей или секретов произвольного формата.

Проверьте доступность сервера только по ожидаемому адресу, папки и тома, сохранность `.env` и результата после перезапуска. Проверки кода — в [руководстве разработчика](docs/DEVELOPMENT.md).

Не публикуйте полный вывод `docker compose config`: в нём могут оказаться подставленные секреты. История тредов, результаты и резервные копии также могут содержать переданные материалы.

## Сообщение об уязвимости

Передайте владельцу репозитория по приватному каналу минимальное воспроизведение, затронутую версию и влияние. Не публикуйте ключи, `.env`, корпоративные документы или рабочий exploit в открытом issue. Для обычных ошибок используйте [памятку диагностики](docs/TROUBLESHOOTING.md).
