# Проведение нагрузочного тестирования

> **Архивный отчёт модели; исходный текст ниже сохранён без исправления выводов.** Он содержит ошибочную трактовку `nt_errors`: сырой `passes=1` означает одну неуспешную проверку, `fails=903` — 903 успешные; `rate=1/904≈0,001106` корректен. Текущий runner выдаёт `failed_requests` / `ok_requests`. Нулевой `error_rate` последнего окна не означает отсутствие ошибок во всём тесте. Формулировка PASS не заменяет вычисленный результат `INCONCLUSIVE` / `PARTIAL` и не доказывает прохождение профиля 2000 RPS. Метрики симулятора не измеряют влияние k6 на цель. [Подробное пояснение](README.md#почему-в-старом-отчёте-903-fails).

Прогон завершён (test_status=completed, stop_reason пуст), поэтому результаты пригодны для оценки по заданным SLA.

ВЕРДИКТ по явным критериям задачи (20 rps, p95<=800 мс, ошибки<=1%): PASS по детерминированным метрикам раннера. Фактически сгенерированная нагрузка 19.2 rps (окно 5 с; суммарно 904 запроса за ramp 10 с + плато 40 с, что ровно соответствует модели разгона при target_rps=20), p95 = 150.5 мс (avg 104.9, p99 = 169.8, max 194.0), error_rate = 0.0. Оба порога выполнены с большим запасом, стоп-пороги (p95>2500 мс, ошибки>15%) не срабатывали. Цель «checkout-api держит 20 rps» на этом уровне подтверждена.

ЧТО НЕ ПОДТВЕРЖДЕНО / ОГРАНИЧЕНИЯ:
1) Диагностический статус прогона PARTIAL / INCONCLUSIVE: по checkout-api получено по одному наблюдению на метрику (count=1, mad=0), устойчивых плато в телеметрии нет (одна transition-фаза), ряды по ряду сервисов неполные. Это ограничение диагностического контура, а не доказательство деградации: отклонений от baseline нет (p95 141.9 мс, error_rate 0.0023, cpu 0.240, throttle 0, restarts 0).
2) Внутреннее противоречие в отчёте: блок nt_errors показывает fails=903, passes=1 при rate=0.0011, тогда как error_rate=0.0 и summary по http_reqs=904/p95=150 мс согласуются с почти нулевой долей ошибок. Расхождение считаю дефектом представления метрики (свёрнутые/перепутанные поля), а не признаком 99.9% отказов: при таком уровне отказов выросли бы и клиентский error_rate, и сервисный (наблюдалось 0.234%). Тем не менее как независимо подтверждённый факт это не зафиксировано.
3) Причинная цепочка «нагрузка → зависимость → ошибки/латентность» не проверена: список зависимостей checkout-api в evidence пуст, CONFLUENCE_UNAVAILABLE. Заявленные в анализе rps 503.87 / http_4xx 4.02 / http_5xx 1.18 относятся к агрегату сервиса/namespace, а не к нашему трафику, и как индикатор ступени нагрузки не используются.
4) Задача Jira NT-123 этим прогоном НЕ закрыта: там заявлены 2000 RPS, ступени 1000→2000, SLA p95<500 мс и сервис order-service. Стенд checkout в capabilities ограничен max_rps=200, max_vus=50, max_duration=300 с, поэтому проверка 2000 RPS на нём невозможна в принципе; 20 rps — это малый дымовой/предварительный профиль, его PASS не переносится на релизный профиль 1.42 (в т.ч. после смены сериализации заказов ORD-4471).

СЛЕДУЮЩИЕ ШАГИ (вне бюджета этой сессии): (а) согласовать реальные условия NT-123 со стенд-менеджером — нужен стенд с max_rps >= 2000 и профилем ступеней; (б) зафиксировать перечень зависимостей checkout-api/order-service и их метрики для трендового и ступенчатого анализа; (в) исправить/подтвердить семантику счётчика nt_errors в отчёте раннера; (г) при подтверждении 20-rps уровня повторить на более длинном плато (до 300 с) для набора точек внутри плато.
