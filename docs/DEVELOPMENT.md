# Разработка и проверка изменений

[Документация](README.md) / Разработка

Начните с [локальной установки](GETTING_STARTED.md). Все команды ниже запускаются из корня репозитория. Общая схема компонентов — в [архитектуре](ARCHITECTURE.md).

## Основные проверки

Windows PowerShell:

```powershell
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m pytest
npm.cmd --prefix web run test:engine
npm.cmd --prefix web run build
git diff --check
```

Linux/macOS:

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m pytest
npm --prefix web run test:engine
npm --prefix web run build
git diff --check
```

Тесты Python подменяют модель и внешние ответы; рабочие ключи не нужны. Frontend-тесты проверяют движок, а сборка — типы TypeScript и создание bundle. Для `test:engine` используйте Node 22, как в CI. Успешная сборка не заменяет проверку экрана в браузере или проверку прав на вашем сервере Jira.

Браузерные регрессии стоят в CI и запускаются локально после сборки:

```powershell
.venv\Scripts\python.exe -m pip install -e ".[uitest]"
.venv\Scripts\python.exe -m playwright install chromium
.venv\Scripts\python.exe web/tests/browser_regressions.py
```

Браузер берётся из кеша Playwright — Windows, Linux и macOS одинаково; свой путь задаётся через `UI_TEST_CHROME`. Проверки поднимают локальный тестовый API без модели и без записи реальных настроек. Они включают базовые сценарии из `browser_smoke.py`, Markdown без выполнения скриптов, ввод массивов, сохранение настроек при одновременном редактировании и закрытии окна, снятие черновика секрета при закрытии, клавиатуру и фокус в модальном окне, ошибки публикаций, просроченный токен и восстановление связи. Снимки экрана сохраняются в `.tmp/ui-smoke`.

| Изменение | Минимальная содержательная проверка |
| :--- | :--- |
| Роли, маршруты, источники | Затронутые Python-тесты и сценарий на тестовом комплекте |
| Jira/Confluence | Тесты транспорта, планов, преобразования документов и ошибок |
| UI-манифест | Контрактные Python-тесты, engine-тесты и сборка frontend |
| Верстка frontend | Сборка, браузерные регрессии и визуальная проверка изменённых состояний |
| Документация | Команды, пути, ссылки, изображения, согласованность с кодом |

Полный состав CI описан в [workflow](../.github/workflows/ci.yml): Python 3.11–3.13, Ruff, pytest, frontend-тесты, сборка, браузерные регрессии и аудиты зависимостей. Не фиксируйте число прошедших тестов как постоянное свойство продукта.

## CLI-демо

`run_demo.py` — демонстрация трёх заданных запросов в одном треде с учётом кеша. Она не запускает frontend и не является универсальной CLI-формой выбора файлов. Каждый реальный запуск обращается к LLM.

Скрипт не обрабатывает интерактивные подтверждения. Чтобы посмотреть только генерацию и стоимость без внешней публикации, выполните в отдельном терминале:

```powershell
$env:PUBLISH_TARGET="none"
$env:PIPELINE_REQUIRE_APPROVAL="0"
.venv\Scripts\python.exe run_demo.py
```

Linux/macOS:

```bash
PUBLISH_TARGET=none PIPELINE_REQUIRE_APPROVAL=0 .venv/bin/python run_demo.py
```

Для автоматического сохранения именно в файлы задайте `PUBLISH_TARGET=file`, `CONFLUENCE_PUBLISH=1`, `CONFLUENCE_PUBLISH_MODE=each` и `PUBLISH_REQUIRE_APPROVAL=0` в окружении этого демо. Обычный интерактивный UI лучше оставлять с согласованием.

Дополнительные флаги смотрите в начале [`run_demo.py`](../run_demo.py): `--bad` меняет стабильность префикса для сравнения, `--json` выводит данные по ходам, `--log` задаёт журнал вызовов. Эти эксперименты тоже тратят токены. Исходные журналы опубликованных экспериментов — в [`docs/measurements/`](measurements/).

## Собственный Python-рантайм

Для запуска из скрипта граф компилируют с собственным checkpointer и, при необходимости, store. Импортируемые сервером готовые `graph` скомпилированы без них: сервер предоставляет хранение сам.

Общий порядок:

1. Открыть `open_checkpointer()` и `open_store()` из `agent.checkpointer`.
2. Скомпилировать builder нужного графа с этими объектами.
3. Передать постоянный `configurable.thread_id` и параметры материалов.
4. Выполнить `invoke`/`stream` и проверить наличие interrupt.
5. Если процесс интерактивный — получить решение человека и передать `Command(resume=...)` в тот же тред.

Для PostgreSQL дополнительно установите extra:

```powershell
.venv\Scripts\python.exe -m pip install -e ".[postgres]"
```

Задайте `CHECKPOINT_BACKEND=postgres` и доступный вашему процессу `POSTGRES_URI`. Внутри Compose имя хоста — `postgres`; с хоста такой адрес недоступен. Штатный Compose не публикует порт базы на localhost.

## LangGraph Studio

Тот же backend объявляет графы в `langgraph.json`; Studio можно подключить к нему по адресу, который выдаёт установленный CLI. Учётная запись и доступ к сервису Studio относятся к этому отдельному инструменту и не нужны собственному frontend Orbita.

Минимальный ввод графа:

```json
{
  "messages": [
    {"role": "user", "content": "Сверь пакет документов и перечисли расхождения."}
  ]
}
```

Для `audit` передайте `input_dir=partial-refund-package` в configurable/context параметрах запуска. Имена полей берутся из `Options` выбранного графа и UI-манифеста.

Обычное согласие на остановке имеет вид `{"decision":"approved"}`, отказ — `{"decision":"rejected","reason":"Нужно уточнение"}`. Ответ направляется в существующий interrupt, а не отправляется новым сообщением пользователя.

## Добавление сценария

Для последовательности ролей используйте существующие `Role`, `Pipeline` и `builder.py`. Если процесс принципиально другой, можно собрать собственный `StateGraph`, как у `update`.

1. Добавьте граф и описание его входа/состояния.
2. Зарегистрируйте граф в `langgraph.json`.
3. Добавьте манифест в `src/agent/ui_engine/graph_manifests/` и в список `MANIFESTS` его `__init__.py`; `registry.py` регистрирует этот список. При новых ресурсах расширьте также registry.
4. Проверьте соответствие узлов манифеста реальной топологии.
5. Покройте существенные ветки: пустой вход, успешный результат, отказ/подтверждение, ошибка внешнего действия.
6. Добавьте пример в [сценарии](WORKFLOWS.md) и тестовые материалы.

Новый frontend-код не нужен, если существующие виджеты покрывают ввод и результаты. Подробный контракт — в [UI engine](UI_ENGINE_IMPLEMENTATION.md).

## Как поддерживать документацию

| Изменение кода | Обновить |
| :--- | :--- |
| Переменная конфигурации | `.env.example`, `CONFIGURATION.md`; комментарий шаблона также попадёт в UI настроек |
| Новый формат/лимит входа | `INPUTS.md` и соответствующий сценарий |
| Новая роль или граф | `README.md`, `README.en.md`, `WORKFLOWS.md`, `ARCHITECTURE.md` |
| Запуск, порт, Docker/volume | `GETTING_STARTED.md`, `DEPLOYMENT.md` |
| Пользовательское действие | `USER_GUIDE.md` и нужный кадр в `VISUALS.md` |
| Изменение известных результатов примера | `TEST_DATA.md` и проверка соответствующих фикстур |

Отчёты аудитов и измерений сохраняйте как датированные документы. Не переписывайте старые цифры так, будто это результаты нового прогона. Схемы Mermaid хранятся рядом с поясняющим текстом; правила скриншотов — в [визуальных материалах](VISUALS.md).
